### Parser findings worth remembering

- Three pages include the **non-`Annotated`** variant on purpose (e.g.
  `path-params-numeric-validations.md` explains parameter order with it). Blindly switching to
  `_an_py310` would contradict the prose, so the referenced file wins and `_an_py310` is only
  a fallback for missing files.
- `{**old_dict, ...}` in Python code must not count as include syntax: the check requires
  whitespace after `{*`.
- Link text can itself contain code (``[`orjson`](https://...)``), so links are rewritten
  before code spans are protected.

### Hard negatives and a false-negative estimate

For each answerable query, the 2 nearest sections on other pages (bge-small embeddings,
readable by the principal) were judged. Of 366 judged candidates: grade 0 = 170, grade 1 =
127, grade 2 = 69. Only grade-0 candidates became hard negatives (170 on 115 queries).
**54% of the nearest other-page sections were judged relevant**, so v1, which only knows the
source section, has many false negatives. This is the motivation for pooling in v2 (M4).
These are judge grades; the judge agrees closely with Claude's labels (below), which has not
been checked against a person.

## Judge calibration (`experiments/20261018T122706Z_calibrate/report.json`)

- Judge `openai/gpt-5.4-nano` (temperature 0, no reasoning, ADR 0003); rubric
  `src/docseek/eval/prompts/relevance_judge.md`, version `2cf46a092009` (unchanged: no
  revision round was needed).
- 100 pairs sampled with seed 13 (35 golden-relevant, 35 hard negatives, 30 other sections of
  the same doc_type, shuffled), labelled **by Claude** from the query and section text only,
  without the pair's stratum or any judge score. The labels were committed (`2d92a9c`)
  before the judge was run on them.
- Labelling rule used: 2 = the section answers the question; 1 = same specific topic and
  gives part of the answer; 0 = only the same broad area, or unrelated.

| Metric | Value |
|---|---|
| Weighted κ, linear / quadratic | **0.922** / 0.958 |
| Unweighted κ | 0.865 |
| Exact agreement | 0.93 (93/100) |
| Label counts, Claude (0/1/2) | 61 / 10 / 29 |
| Label counts, judge (0/1/2) | 63 / 5 / 32 |
| Position bias (query-first vs section-first prompt) | 97% same grade, κ 0.966, mean shift −0.03 |
| Length bias, Spearman(section length, grade) | judge 0.138, Claude 0.151 |

Confusion (rows Claude 0/1/2, columns judge 0/1/2): `[[60, 1, 0], [3, 4, 3], [0, 0, 29]]`.
Exact agreement by stratum: relevant 0.914, hard negative 0.914, same doc_type 0.967.

All 7 disagreements are one grade apart, and 5 of them are pairs Claude graded 1: the judge
uses grade 1 half as often (5 vs 10) and resolves partial matches to 0 or 2. Examples:
"sub-dependencies" vs the basic dependency section (Claude 1, judge 0); FileResponse shown
only inside an example (Claude 1, judge 2); a superseded doc that still explains the reason
for a limit (Claude 1, judge 2).

**Caveats — read before quoting this κ.**
1. The reference labels are by another LLM, not a person. Two LLMs can share blind spots,
   so this κ is likely **higher** than judge-vs-human agreement would be. It shows the judge
   is consistent with a careful, rule-based labelling; it does not show agreement with
   human users.
2. Claude also wrote the golden review and saw some sections in that step; 35 of the pairs
   are golden-relevant sections Claude had reviewed, which may make those labels easier.
3. A human labelling pass on the same 100 pairs (`docseek eval label`, `annotator: human`)
   would turn this into the κ the spec asks for; the pairs and tooling are ready.

## Judge reliability summary

With the caveats above, the judge is used as planned for v2 pooling (M4). Its main weakness
is the middle grade: it rarely gives 1, so graded metrics (nDCG) built on judge labels will
be more polarised than on careful labels.

## Engineering notes

- **Budget-driven model change (ADR 0003).** The M0 models would have cost an estimated
  $1.2-3.5 for M1 alone. Both are now the cheapest structured-output models with thinking
  turned off; a project-wide spend ledger refuses OpenAI calls past $2.00.
- **LiteLLM's retry needs `tenacity`** (an optional dependency). Without it, the first
  transient Gemini 503 crashed the full synth run with an ImportError.
- **Every retry needs its own cache key.** Retry prompts that quoted the same problems hit
  the cached bad reply; the attempt number is now part of the feedback.
- **Windows cp1252 console** crashed on "Δ" in CLI output; output now replaces unencodable
  characters.
- `ranx` JIT-compiles with numba on first use (about 2 minutes once, cached afterwards).

## Analysis questions

**Which retriever does this golden set favour?** Lexical retrieval, most likely. Median
overlap is 0.625, and only 45 of 191 styled queries are paraphrases (mean overlap 0.323
against ~0.7 for the other styles). Relevance comes from the section that produced the
query, and the 54% relevant rate among nearest neighbours shows that other good sections go
unlabelled. Both effects reward retrievers that match the source section's wording. The
33 Claude-written queries did not reduce this (overlap 0.645 vs 0.610). M2-M3 should report
metrics per style, and v2 pooling (M4) is needed before dense vs BM25 conclusions are
trusted.

**Why judge relevance per section, not per chunk?** See ADR 0002: section ids are stable
across chunking strategies, chunk hits map back to the best-ranked section, so M5's chunking
ablation is measured on the same labels without double-counting split sections.
