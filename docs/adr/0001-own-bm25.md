# ADR 0001: Implement BM25 ourselves, use `bm25s` only as a reference

- **Status:** Proposed (M0). To be revisited and marked Accepted or Rejected in M2, with
  measurements from `experiments/`.
- **Date:** 2026-10-18
- **Deciders:** project owner

## Context

DocSeek's first retrieval baseline is lexical search over FastAPI docs. Two options:

1. Use a library (`bm25s`, Elasticsearch/OpenSearch, Tantivy, Pyserini).
2. Implement tokenizer, inverted index and BM25 scoring ourselves, and use a library only to
   cross-check scores, rankings and speed.

Forces:

- **Learning goal.** The project exists to understand each retrieval layer. A library hides
  exactly the parts we want to study: tokenization, document-length normalisation (`b`),
  term-frequency saturation (`k1`) and field weighting.
- **Domain-specific tokenization.** Technical docs are full of identifiers
  (`BackgroundTasks`, `response_model`, `@app.get`). We want a code-aware tokenizer that
  splits `camelCase`/`snake_case` while also keeping the original token. Most libraries
  let us plug in a tokenizer, but field weighting (BM25F-style over `title`,
  `section_path`, `body`, `code`) usually is not available or not transparent.
- **ACL and filters.** Permission filtering must happen inside the retriever
  (pre-filter or over-fetch then post-filter). Owning the index makes both options easy to
  implement and to measure.
- **Scale.** About 150 indexable pages plus a few dozen internal KB documents: a pure Python
  plus NumPy index is fast enough, so a search server would be operational overhead.
- **Risk.** Hand-written scoring can be subtly wrong.

## Decision (proposed)

Implement `lexical/tokenizer.py`, `lexical/inverted_index.py`, `lexical/tfidf.py` and
`lexical/bm25.py` ourselves. Add a `bm25s_lib` retriever with the same tokenizer as a
reference implementation.

## Consequences

- We need hand-computed unit tests for the BM25 score, and an agreement check against
  `bm25s` (top-10 overlap with the same tokenizer; target ≥ 0.8, or explain the gap).
- Index build, persistence and incremental rebuilds become our code to maintain.
- Field weighting and code-aware tokenization can be ablated freely.

## When a library is the better choice

To be filled in M2 from measured index size, build time, query latency and agreement with
`bm25s`, and in general: large corpora, multi-tenant serving, rich query syntax, or teams
without a reason to own ranking code.
