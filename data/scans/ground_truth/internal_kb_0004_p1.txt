Rotating JWT Signing Keys
This document outlines the mandatory rotation procedure for JSON Web Token (JWT) signing keys within
our infrastructure. All authentication ﬂows utilizing OAuth2PasswordBearer depend on these cryptographic
keys to verify token integrity. Proper rotation cycles are critical to minimizing the blast radius of a potential
key compromise.
Rotation Schedule and Persistence
All JWT signing keys must be rotated every 30 days. This cadence is enforced to limit the window of
opportunity for unauthorized token generation. All keys are stored and managed within the vault-hsm-2
HSM cluster. Direct access to the private key material is restricted to the security-team; service identities
retrieve signing material via the established HSM integration protocols.
Grace Period and Validation
To prevent widespread authentication failures during the propagation of new keys, we implement a strict
grace period. The previous signing key remains valid for 24 hours following the rotation event. During this
24-hour window, the authentication middleware must support dual-key veriﬁcation. When a request
reaches the API, the OAuth2PasswordBearer dependency attempts to validate the incoming JWT against
the current active key. If validation fails, the system must fallback to checking the signature against the
previous key stored in the vault-hsm-2 cluster.
Applications must update their local key caches at the start of each rotation. After the 24-hour grace period
expires, the previous key must be explicitly revoked and removed from the active veriﬁcation set to ensure
the system does not accept stale tokens. Failure to adhere to these rotation intervals or the grace period
duration constitutes a violation of our security-team standards.
