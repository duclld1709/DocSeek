# Handling 429 spikes from the card network { #handling-429-spikes-from-the-card-network }

## Overview { #overview }

This runbook outlines the operational procedure for the payments-team when encountering rate-limiting issues with our upstream card network provider. When our integration receives an excessive volume of HTTP 429 Too Many Requests responses, it indicates that our request throughput has exceeded the network's defined capacity. Failure to throttle these requests can lead to downstream instability, extended circuit-breaker timeouts, and potential degradation of other payment processing paths.

## Detection and Response { #detection-and-response }

Monitoring alerts are configured to trigger when the error rate for 429 status codes exceeds 200 responses per minute. Upon receiving an alert, engineers must verify the spike via the Grafana dashboard titled "Upstream Gateway Metrics." If the current rate remains sustained above 200 HTTP 429 responses per minute, immediate load shedding is required to preserve system integrity.

## Enabling Load Shedding { #enabling-load-shedding }

To mitigate the spike, the `shed-load` feature flag must be enabled immediately. This flag activates a middleware component in our FastAPI application that rejects non-critical traffic before it reaches the network client, effectively reducing the request volume. Follow these steps to engage the mechanism:

1. Access the internal feature management console.
2. Locate the `shed-load` flag.
3. Set the state to `enabled` for the production environment.
4. Confirm that the egress traffic rate to the card network decreases.

Once the upstream network stabilizes and the 429 rate drops consistently below the threshold for 15 minutes, the `shed-load` flag should be disabled to restore full service capacity. Document the incident in the internal tracking system, including the start time, duration of the spike, and the total volume of 429 responses observed.
