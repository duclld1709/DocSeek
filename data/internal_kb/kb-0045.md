# Error responses { #error-responses }

This document outlines the standard error handling pattern for services managed by the api-platform-team. Consistent error reporting is critical for client integration stability and observability across our infrastructure.

## Response format { #response-format }

All error responses must use the `application/problem+json` media type as defined in RFC 7807. This ensures that clients can programmatically parse failure states without relying on fragile string matching. When a request fails, the API must return a structured object containing a machine-readable error type, a human-readable title, and the specific status code associated with the failure.

## Implementation details { #implementation-details }

To standardize error propagation, developers must utilize FastAPI's built-in `HTTPException`. When a validation or business logic error occurs, the handler should raise an `HTTPException` containing a specific Acme error code within the `detail` field. 

```python
raise HTTPException(
    status_code=400,
    detail="ERR_INVALID_TRANSACTION_AMOUNT"
)
```

By embedding the unique Acme error code directly in the `detail` field, we enable our monitoring tools to aggregate issues by error type rather than just HTTP status codes. Avoid using raw strings or generic error messages in the `detail` field, as these often obscure the root cause during production debugging. Always map internal exceptions to these defined codes at the service boundary to prevent leaking stack traces or internal implementation details to the client.

## Best practices { #best-practices }

Ensure that all custom exception handlers return the `application/problem+json` structure. If a service requires additional context beyond the error code, include it in an `extensions` dictionary within the JSON payload. This keeps the primary `detail` field clean for automated parsing while providing necessary metadata for complex debugging scenarios.
