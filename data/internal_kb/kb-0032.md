# Request and Response Validation { #request-and-response-validation }

## Overview { #overview }

This document outlines the mandatory patterns for request and response validation within our FastAPI services, maintained by the api-platform-team. To maintain service integrity and prevent accidental data exposure, all endpoints must enforce strict input and output schemas. Every path operation must declare a `response_model` explicitly. This ensures that Pydantic models filter the internal data structures, preventing internal fields from leaking into the public API responses. Developers are prohibited from returning raw dictionary objects or database models directly from path operation functions.

## Monetary Precision { #monetary-precision }

Handling financial data requires absolute precision to avoid floating-point errors. Consequently, all monetary amounts must be represented as integers in minor units (e.g., cents for USD) throughout our codebase. Never use floating-point numbers for currency fields, as they introduce rounding inaccuracies during arithmetic operations. When defining Pydantic models for request bodies or the `response_model`, use the `int` type for all currency-related fields. If an incoming request contains a float for a monetary value, the schema validation will automatically raise a validation error, which is the desired behavior to maintain system consistency. 

## Implementation Standards { #implementation-standards }

When implementing new endpoints, ensure that the `response_model` is defined in the decorator. This practice provides automatic OpenAPI documentation generation and runtime validation. If a response model is omitted, the service risks leaking internal database identifiers or sensitive metadata fields. For complex nested objects, define specific sub-models to keep the response contract clean. Adhering to these standards ensures that our internal APIs remain predictable, secure, and maintainable across all services under the api-platform-team domain.
