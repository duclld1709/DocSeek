# Card processor timeouts { #card-processor-timeouts }

## Overview { #overview }

This runbook outlines the operational requirements for handling latency when communicating with our upstream card processor. The `payments-team` maintains the infrastructure responsible for these integration points. Maintaining predictable latency is critical to our service level objectives, and we enforce a strict timeout of 10 seconds for all outbound requests to the processor API. If a request exceeds this duration, the connection is forcibly terminated to prevent cascading failures across our FastAPI services.

## Retry and error handling { #retry-and-error-handling }

When a request results in a timeout, the service is configured to perform exactly one automatic retry of the authorization attempt. This retry mechanism is isolated to the initial connection phase. If the second attempt also fails due to a timeout, the system must immediately cease further attempts and return an HTTP 504 Gateway Timeout status code to the original caller. This prevents exhausted resources in our upstream worker threads.

## Implementation details { #implementation-details }

Engineers should implement this logic within the service layer rather than the controller. Utilize `Depends` to inject the necessary HTTP client session or processor configuration into your route handlers. By leveraging `Depends`, we ensure that timeout configurations remain consistent across all payment endpoints and simplify unit testing by allowing for dependency mocking. Ensure that all timeout exceptions are caught explicitly before the final 504 response is generated to avoid leaking internal stack traces. If you observe an increase in 504 errors, check the current latency metrics for the provider in our dashboard before investigating local infrastructure bottlenecks.
