# Webhook delivery and retries { #webhook-delivery-and-retries }

## Overview { #overview }

This document outlines the legacy delivery mechanism for asynchronous webhook notifications managed by the api-platform-team. This system is currently marked as deprecated and is slated for complete decommissioning. New integrations must utilize the V2 delivery service to ensure compliance with current security and reliability standards.

## Delivery Logic { #delivery-logic }

When an event is triggered, the notification service attempts to deliver the payload to the subscriber's configured endpoint via a POST request. The system expects a 2xx HTTP status code as an acknowledgment of successful receipt. If the endpoint returns a 4xx or 5xx status code, or if the connection times out, the system initiates a retry sequence. Failed webhook deliveries are retried 3 times over 1 hour. These retries follow an exponential backoff strategy to prevent overwhelming the downstream service. If all retries are exhausted without a successful delivery, the event is marked as failed in the database, and the notification is discarded. No further automated attempts will be made for that specific event.

## Implementation Details { #implementation-details }

The current architecture relies on a task queue powered by Celery and Redis to handle the delivery lifecycle. Engineers interacting with these endpoints should note that headers include a custom X-Acme-Signature for payload verification. Because this version is deprecated, monitoring and alerting for these specific retry jobs have been de-prioritized. Teams should prioritize migrating existing webhooks to the current service, which offers improved observability and configurable retry policies. Please contact the api-platform-team on Slack if you require assistance with the migration process or need access to legacy failure logs.
