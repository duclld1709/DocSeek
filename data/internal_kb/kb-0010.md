# Refund API behaviour { #refund-api-behaviour }

## Overview { #overview }

This document outlines the operational constraints for the refund service managed by the payments-team. All API consumers must adhere to these business rules to ensure consistency across our transaction lifecycle. When a request violates these constraints, the service must return a 400-series `HTTPException` to signal the client-side error clearly.

## Time-based constraints { #time-based-constraints }

Refunds are strictly permitted for a window of 120 days following the original capture event. Any request submitted after this period will be rejected. When implementing these checks in our FastAPI routes, ensure that timestamp validation is performed against the database-stored capture date rather than the client-provided payload. If the 120-day threshold is exceeded, the endpoint should raise an `HTTPException` with a status code of 422, detailing that the transaction is no longer eligible for refund processing.

## Partial refund limits { #partial-refund-limits }

To prevent excessive fragmentation of payment records, we enforce a hard limit of 10 partial refunds per individual payment ID. This limit is tracked at the database level using the `refund_count` metadata attribute associated with each transaction. When an incoming request attempts to exceed this limit, the service logic must trigger an `HTTPException` with a status code of 403, indicating that the maximum number of partial refunds has been reached. Developers should ensure that idempotency keys are utilized correctly when retrying failed requests to avoid unnecessary incrementing of the refund count. These constraints are enforced globally across all regions to maintain parity in our ledger integrity.
