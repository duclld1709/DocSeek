# Health check endpoints { #health-check-endpoints }

## Overview { #overview }

All services deployed within the Acme Payments infrastructure must implement standard health check endpoints to facilitate automated lifecycle management within our Kubernetes clusters. These endpoints allow the orchestrator to monitor service health and ensure traffic is routed only to instances capable of processing requests.

## Endpoints { #endpoints }

Every service is required to expose the following two endpoints:

* `/healthz`: This endpoint serves as the liveness probe. It indicates whether the application process is running and responsive. If this check fails, the orchestrator will restart the container.
* `/readyz`: This endpoint serves as the readiness probe. It indicates whether the service is prepared to accept incoming traffic. The readiness check must return a non-200 status code while database migrations are running to prevent the load balancer from routing traffic to an unstable pod.

## Implementation { #implementation }

In our FastAPI services, these checks should be implemented as lightweight, synchronous routes. Avoid performing complex logic or external network calls within these handlers, as blocking operations could time out or cause cascading failures. If a service depends on a database, the readiness check should verify connectivity but exclude high-latency operations. Keep the dependency surface area minimal to ensure the orchestrator receives a definitive response within the configured timeout window.

## Operational Considerations { #operational-considerations }

Our SRE-team monitors these endpoints to track service availability trends over time. Ensure that logs for these endpoints are excluded from standard application logging aggregators to prevent noise. By maintaining consistent implementations across all services, we reduce the complexity of our deployment pipeline and improve the reliability of our traffic management strategies.
