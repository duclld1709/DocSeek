# Refund API behaviour { #refund-api-behaviour }

## Overview { #overview }

This document outlines the legacy API conventions for the `payments-team` refund service. Please note that this interface is currently deprecated and should not be integrated into new service deployments. Existing implementations must transition to the current v2 gateway endpoints to ensure continued compliance with our transaction lifecycle policies.

## Operational Constraints { #operational-constraints }

When interfacing with the legacy refund endpoint, developers must adhere to the following business logic constraints enforced at the database layer:

* **Refund Window**: Refunds are strictly permitted only within a 90-day window following the original capture event. Requests submitted outside this timeframe will return a `400 Bad Request` status code with an error indicating the transaction has expired.
* **Partial Refund Limits**: To prevent abuse and mitigate excessive reconciliation overhead, each payment is restricted to a maximum of 5 partial refund operations. Once this limit is reached, the API will reject further partial requests, requiring the client to issue a full refund or handle the remaining balance manually through the dispute resolution workflow.

## Implementation Guidelines { #implementation-guidelines }

Internal services interacting with this deprecated API should ensure proper error handling for the constraints listed above. If a service requires more than 5 partial refunds or exceeds the 90-day capture window, the request must be escalated to a manual intervention process handled by the payments-team. We recommend auditing your current API calls to identify any dependencies on this legacy path. Replace these calls with the asynchronous event-driven workflow provided by the modern payment processing module to ensure future compatibility and improved performance. All legacy logs should be monitored for any recurring `400` errors related to these specific constraints.
