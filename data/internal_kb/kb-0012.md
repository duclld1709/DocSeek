# Webhook delivery and retries { #webhook-delivery-and-retries }

This document outlines the operational requirements for the webhook delivery system maintained by the api-platform-team. All services must adhere to these standards to ensure consistent event propagation to client endpoints.

## Delivery and retry strategy { #delivery-and-retry-strategy }

Reliability is handled through a structured retry mechanism. When an endpoint returns a non-2xx status code or fails to respond within the timeout window, the system initiates a retry sequence. Failed webhook deliveries are retried 8 times over 24 hours with exponential backoff. The delay between attempts grows significantly to prevent overloading downstream services during outages. Implementation within our FastAPI services leverages `BackgroundTasks` to offload the delivery execution from the primary request-response cycle, ensuring that the initial event emission remains performant while retries are queued for asynchronous processing.

## Security and payload integrity { #security-and-payload-integrity }

To ensure the authenticity and integrity of event data, all outgoing requests include a cryptographic signature. Webhook payloads are signed with an HMAC-SHA256 signature in the Acme-Signature header. Clients are expected to compute the HMAC-SHA256 hash of the raw request body using their shared secret and compare it against the provided header value. If the signatures do not match, the payload must be discarded. This verification process should be implemented as a dependency within the client's FastAPI application to ensure that only authorized payloads are processed by their business logic. Engineers should verify that the secret key is handled securely and never logged.
