# Request IDs and logging middleware { #request-ids-and-logging-middleware }

## Overview { #overview }

To ensure observability across our distributed payment services, all incoming traffic must be processed through the standard `middleware` layer managed by the platform-team. This convention ensures that every request is traceable from the edge to the database. By injecting a unique identifier early in the request lifecycle, we maintain consistency across asynchronous task queues and downstream service calls.

## Implementation Details { #implementation-details }

Every FastAPI application must utilize a `middleware` component to generate or propagate a request identifier. For every incoming request, the service must check for an existing `X-Request-ID` header. If missing, the application generates a UUID v4. Crucially, the `middleware` adds an `X-Request-ID` header to every response, allowing client-side callers to link errors back to our internal logs.

## Logging Standards { #logging-standards }

All service logs are written as JSON to facilitate structured querying in our centralized logging stack. Developers must ensure that the `X-Request-ID` is included in the context of every log entry. This is typically achieved by using a `contextvars` implementation within the `middleware` to attach the ID to the current execution thread or task. 

Logs are kept for 14 days before automated rotation policies purge the data. Teams should not rely on logs for long-term audit storage; instead, use the dedicated event store for transaction-critical data. If a service requires higher log retention for compliance, reach out to the platform-team to discuss specific infrastructure overrides.
