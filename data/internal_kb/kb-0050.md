# KYC review queue backlog { #kyc-review-queue-backlog }

## Overview { #overview }

This runbook outlines the operational response protocol for the KYC review queue managed by the risk-team. The queue tracks pending merchant verification requests that require manual intervention by compliance analysts. Maintaining a low latency in this process is critical for merchant onboarding and platform compliance.

## Monitoring and Incident Response { #monitoring-and-incident-response }

The engineering team monitors the queue depth via our internal observability dashboard. When the KYC review queue has more than 500 pending merchants, the on-call engineer must open an incident. This threshold is set to prevent downstream bottlenecks in our FastAPI-based merchant verification services and to ensure that SLA commitments are met for new account activations.

### Incident Procedure { #incident-procedure }

Upon triggering the incident, the following steps are mandatory:

1. Verify the queue count via the `kyc_queue_depth` metric in Prometheus.
2. Confirm that the backlog is not caused by a transient API failure or a stuck background worker process in our Python services.
3. Communicate the status in the internal #risk-ops-alerts channel.
4. If the backlog persists due to volume, escalate to the compliance lead to request additional manual review resources.

## Technical Context { #technical-context }

The queue is implemented as a PostgreSQL table queried by our internal risk-engine service. If the backlog is driven by high ingestion rates rather than analyst throughput, evaluate the current rate-limiting policies on the `/v1/merchants/onboarding` endpoint. Ensure that the background jobs responsible for state transitions are not experiencing high latency or deadlocks. Do not attempt to clear the queue by force-updating database records without prior approval from the data integrity lead.
