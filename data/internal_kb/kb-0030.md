# Read replicas for ledger queries { #read-replicas-for-ledger-queries }

## Context and decision { #context-and-decision }

To ensure the stability of the primary transaction database, the platform-team has decided to offload all ledger reporting queries to PostgreSQL logical replicas. Direct read access to the primary database for analytical or reporting purposes creates unnecessary lock contention and resource exhaustion risks. By offloading these operations, we protect the primary instance from high-latency queries that could otherwise impact write throughput and transaction consistency.

All services interacting with the ledger must configure their database connection pools to target the designated read-replica endpoints. Developers must ensure that these queries are non-mutating and specifically designed for read-only workloads. Any attempt to execute write operations against a replica will result in a connection error, as the replication stream is strictly unidirectional.

## Monitoring and operational requirements { #monitoring-and-operational-requirements }

Strict adherence to replication latency thresholds is required to maintain data consistency for reporting clients. We have implemented automated monitoring to track the replica lag between the primary and the secondary instances. If the replica lag exceeds 5 seconds, the platform-team on-call engineer will be paged immediately via our incident response system. 

Engineers should assume that data read from these replicas is eventually consistent. If an application requires read-after-write consistency, the service must perform the read against the primary database. However, such instances should be rare and documented as exceptions. The platform-team reserves the right to throttle or terminate queries that exceed defined execution time limits on the replica cluster to preserve overall system health.
