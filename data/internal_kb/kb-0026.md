# Pagination conventions { #pagination-conventions }

All list endpoints within our infrastructure utilize cursor-based pagination. This approach ensures consistent performance when traversing large datasets by avoiding the performance degradation associated with offset-based approaches. To request a subset of data, clients must provide the `starting_after` parameter, which accepts the unique identifier of the last object returned in the previous response.

## Implementation details { #implementation-details }

When defining routes in FastAPI, developers must enforce pagination constraints using the `Query` dependency. The `starting_after` field should be defined as an optional string parameter. To maintain system stability and predictable latency, the maximum page size is strictly capped at 100 items per request. If no limit is explicitly defined by the client, the API defaults to returning 20 items. 

## Request validation { #request-validation }

Controllers must leverage `Query` to validate that the requested limit does not exceed the allowed maximum. If a client attempts to request more than 100 items, the service should return a 422 Unprocessable Entity status code. The `starting_after` parameter should be validated against the resource's primary key index. By standardizing these parameters across all public endpoints, the api-platform-team ensures that client-side integrations remain predictable and performant. Adherence to these limits is mandatory for all production services.
