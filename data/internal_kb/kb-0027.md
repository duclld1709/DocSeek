# API versioning policy { #api-versioning-policy }

## Overview { #overview }

This document outlines the versioning strategy maintained by the api-platform-team for all public-facing endpoints. Our goal is to provide a stable, predictable interface for merchants and partners while allowing for necessary evolution of our payment infrastructure. All services built with FastAPI must adhere to these standards to ensure consistency across the platform.

## Version selection { #version-selection }

The API version is selected with the Acme-Version header. Clients must include this header in every request to ensure the correct schema and logic are applied by the backend. Omitting this header will result in an error or default to the oldest supported version, depending on current environment configurations. We encourage all clients to pin their integration to a specific version to prevent unexpected breaking changes during routine deployments.

## Lifecycle and deprecation { #lifecycle-and-deprecation }

We follow a structured lifecycle for API versions to balance innovation with backward compatibility. When a new version is released, the previous version enters a deprecation phase. Deprecated API versions are supported for 12 months after a new version is released. During this 12-month window, the api-platform-team will issue periodic warnings in response headers to notify developers of the upcoming retirement. 

After the 12-month support period expires, the deprecated version will be decommissioned. Requests made to decommissioned versions will return a 410 Gone status code. It is the responsibility of the integrating team to monitor their usage and migrate to supported versions before the sunset date. We recommend evaluating new versions as they are released to take advantage of performance improvements and new features in our Python-based payment stack.
