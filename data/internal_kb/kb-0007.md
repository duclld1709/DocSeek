# Ledger database connection pool sizing { #ledger-database-connection-pool-sizing }

## Overview { #overview }

This runbook documents the legacy connection pool configuration for the `ledger-service`. This document is currently marked as deprecated, as the infrastructure has been migrated to a newer connection management pattern. Engineering teams should refer to the updated platform documentation for current best practices regarding database resource allocation.

## Configuration { #configuration }

In the legacy architecture, each `ledger-service` pod is strictly limited to opening at most 20 database connections. This hard limit was implemented to prevent connection exhaustion on the primary PostgreSQL instances during high-traffic events. When tuning the pool, ensure that the sum of connections across all active replicas does not exceed the `max_connections` threshold defined in the database cluster configuration. Failure to respect this constraint will result in connection queuing and increased latency for downstream payment operations.

## Troubleshooting { #troubleshooting }

If you observe `OperationalError: FATAL: remaining connection slots are reserved` in the logs, verify that the number of replicas does not exceed the available headroom calculated against the 20-connection limit per pod. If the application requires higher throughput, do not increase the per-pod connection limit. Instead, evaluate the implementation of a sidecar connection pooler like PgBouncer to manage multiplexing effectively. All modifications to these parameters require a review by the platform-team to ensure cluster stability.
