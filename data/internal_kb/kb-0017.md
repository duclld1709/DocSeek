# Leaked API key response { #leaked-api-key-response }

## Incident detection and triage { #incident-detection-and-triage }

When the automated secret scanner identifies a compromised merchant credential, it pushes an event notification directly to the `sec-alerts-critical` Slack channel. The on-call security engineer must acknowledge the alert immediately to initiate the incident response workflow. The triage process involves validating the scope of the exposure by checking the associated merchant account logs for unauthorized access patterns or anomalous transaction volume. If the leak is confirmed, the responder must prioritize the containment phase to prevent further exploitation of the payment infrastructure.

## Revocation procedure { #revocation-procedure }

Per security policy, a leaked merchant API key must be revoked within 1 hour of detection. The engineer shall execute the `revoke_merchant_key` utility via the internal CLI, providing the `merchant_id` and the specific `key_id` identified in the alert. Once the command completes, verify the revocation status by querying the database directly to ensure the `is_active` flag is set to `False`. Do not attempt to rotate the key; the merchant must generate a new credential through the dashboard after the security team clears the incident.

## Post-incident communication { #post-incident-communication }

After successful revocation, update the original alert thread in `sec-alerts-critical` with the timestamp of the revocation and a link to the internal incident report. The security team must then notify the affected merchant via the established secure communication channel, providing instructions on how to secure their environment and generate a new API key. Ensure all actions taken during the remediation are logged in the central security audit trail for compliance auditing. If the breach resulted in unauthorized transactions, escalate to the fraud operations team immediately for further investigation.
