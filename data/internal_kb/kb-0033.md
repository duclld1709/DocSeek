# Restarting the ledger service { #restarting-the-ledger-service }

## Overview { #overview }

This runbook details the standard operating procedure for restarting the `ledger-service` pods within the Acme Payments infrastructure. The `ledger-service` maintains the primary transactional state for our distributed architecture. Strict adherence to this process is required to maintain consistency across all distributed ledger nodes and to ensure financial data integrity during pod lifecycle management.

## Maintenance constraints { #maintenance-constraints }

Operational stability is critical during the daily settlement window. You must never restart the `ledger-service` during the 23:00-01:00 UTC settlement window. Any restarts initiated during this timeframe risk corrupting settlement batch processing or causing reconciliation discrepancies. Always verify the current system time in UTC before executing any commands on the production cluster. If a critical failure occurs during this window, escalate immediately to the platform-team on-call engineer for manual intervention.

## Execution procedure { #execution-procedure }

To perform a rolling restart of the `ledger-service` deployment, use the following procedure to ensure zero downtime and state consistency:

1. Verify the current cluster context is set to the production environment.
2. Initiate a rolling restart of the deployment using `kubectl rollout restart deployment/ledger-service`.
3. Monitor the pod status using `kubectl get pods -l app=ledger-service -w`.
4. You must restart `ledger-service` pods one at a time. Wait for the readiness probe to return a successful status for the new pod before proceeding to terminate the next existing instance.

This sequential approach ensures that the load balancer maintains a steady connection to healthy nodes throughout the transition. If the readiness probe fails to pass within 120 seconds, halt the rollout immediately and inspect the logs of the failing pod to identify configuration drift or connection timeouts. Do not proceed with the restart until the root cause is resolved and the pods are stable.
