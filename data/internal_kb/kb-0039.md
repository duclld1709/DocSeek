# Postmortem of the November 2025 ledger double posting { #postmortem-of-the-november-2025-ledger-double-posting }

## Summary { #summary }

On November 14, 2025, the platform-team identified a data integrity issue within the ledger service. A failure in the message processing logic resulted in 312 ledger entries being posted twice. The incident was triggered by a consumer service that failed to implement idempotency checks, leading to duplicate database commits during a message broker retry cycle.

## Timeline { #timeline }

At 09:14 UTC, the message broker experienced a transient connection timeout, causing a batch of pending events to be requeued. At 09:22 UTC, the ledger consumer processed these events again. Because the service lacked a unique constraint or idempotency key validation, it treated the retried messages as new transactions. By 09:45 UTC, internal monitoring alerts flagged an unexpected spike in ledger balance variance, triggering an immediate investigation by the platform-team.

## Root cause { #root-cause }

The primary root cause was the absence of a request-scoped idempotency key in the ledger consumer's message handler. While the upstream producer successfully implemented at-least-once delivery semantics, the downstream consumer was not designed to handle duplicate messages. When the broker re-delivered the messages following the 09:14 UTC timeout, the application logic executed the transaction service without verifying if the specific message ID had been successfully persisted in the ledger database previously.

## Action items { #action-items }

To prevent recurrence, the platform-team will enforce the following steps: first, implement a mandatory idempotency layer using Redis to track processed message UUIDs for all ledger transactions. Second, we will introduce database-level unique constraints on external reference identifiers to prevent duplicate inserts at the storage layer. Finally, we will conduct a code audit of all consumer services to verify that idempotent processing is standard practice across the platform codebase. These tasks are assigned to the platform-team and are prioritized for the current sprint.
