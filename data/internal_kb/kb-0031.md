# Background work and the job queue { #background-work-and-the-job-queue }

This ADR defines the standards for asynchronous execution within the Acme Payments architecture. Maintaining clear boundaries between ephemeral background tasks and durable job queues is essential for system reliability and auditability.

## FastAPI BackgroundTasks { #fastapi-backgroundtasks }

For non-critical operations that do not require high durability, we utilize `BackgroundTasks` within our FastAPI endpoints. This is strictly reserved for fire-and-forget processes where failure does not impact the integrity of a payment transaction. Currently, the primary use case for `BackgroundTasks` is sending customer receipts. Developers must ensure that logic placed here does not perform database writes that are required for state reconciliation. Because these tasks execute within the application process memory, they are subject to termination if the container restarts.

## Durable job queue requirements { #durable-job-queue-requirements }

Any operation involving the movement of funds or modification of sensitive financial state must be handled by our distributed job queue system, identified by the name `payq`. The `payq` infrastructure provides the necessary persistence, retry logic, and monitoring required for critical financial workflows. All payouts, ledger adjustments, and settlement triggers must be offloaded to this queue. 

By routing these operations through `payq`, the payments-team ensures that even in the event of an application crash, the job state is preserved in the underlying queue storage. This pattern prevents data loss and allows for manual intervention or automated retries should an upstream banking partner return a transient error. Avoid using `BackgroundTasks` for any logic that would leave the system in an inconsistent state if the task fails to complete.
