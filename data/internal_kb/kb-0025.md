# Idempotency keys { #idempotency-keys }

This document outlines the standard for implementing idempotency within our FastAPI services, maintained by the api-platform-team. As of the current active status, all state-changing requests must support idempotency to ensure reliable retries during network failures or client-side errors.

## Implementation requirements { #implementation-requirements }

Clients must include an `Idempotency-Key` header in their requests. The value should be a unique UUID generated by the client for each distinct operation. When the server receives a request with this header, it checks the backing store to determine if the key has been processed previously. If the key exists, the service returns the cached response associated with that key rather than re-executing the business logic. If the key is new, the service processes the request and stores the resulting response.

## Data retention { #data-retention }

Idempotency keys are stored for 24 hours. After this TTL expires, the key is purged from the cache, and a subsequent request with the same key will be treated as a new transaction. Developers must ensure that their API handlers are idempotent-aware, particularly when interacting with external payment gateways or database transactions. If a request is currently in progress for a given key, the system should return a 409 Conflict status code to prevent race conditions. This mechanism ensures that we maintain data integrity while providing a robust interface for our public consumers. Avoid reusing keys across different resource types or endpoints to prevent cache collisions.
