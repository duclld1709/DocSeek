# Router layout per bounded context { #router-layout-per-bounded-context }

## Architectural isolation { #architectural-isolation }

To prevent the monolithic bottleneck as the codebase scales, all services must implement strict domain boundaries. Each bounded context must be isolated into its own `APIRouter` instance. This pattern ensures that domain logic remains decoupled and facilitates independent testing cycles. By encapsulating routes within specific modules, we reduce the complexity of the global namespace and prevent accidental cross-pollination of business logic between disparate domains.

## Router configuration { #router-configuration }

Every service must define clear URL prefixes aligned with the domain's responsibility. Each bounded context has its own `APIRouter` with a URL prefix such as `/payments` or `/payouts`. When initializing these routers in the main application entry point, use the `include_router` method to map these prefixes consistently. This explicit configuration ensures a predictable and discoverable API surface area for internal consumers. Avoid nesting routers beyond a single level to maintain route resolution performance and simplify debugging.

## Governance { #governance }

This structural convention is maintained by the api-platform-team and is required for all new service development. Teams are expected to migrate existing legacy controllers to this `APIRouter` pattern during routine refactoring. Adherence to this layout is verified during the mandatory architectural review process prior to production deployment. Deviations from this standard require explicit approval from the platform team to ensure long-term maintainability of the service mesh.
